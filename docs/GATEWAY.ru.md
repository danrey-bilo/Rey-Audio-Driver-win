# Подписанные устройства Windows: локальный прототип TAG

Результаты ниже относятся к прежним локальным сборкам 2.7. USB-установщик
2.8 не включает TAG и не создаёт системные устройства Windows. Этот опциональный
USB backend остаётся экспериментальным; прежние измерения не квалифицируют 2.8.

Опциональный backend службы Rey использует **оригинальный Thin Audio Gateway
demo 2.0.0.1903**, чтобы предоставлять Windows аудиовход и аудиовыход без загрузки
Rey ACX. На стенде 03.10.2026 проверены действующие подписи SYS/CAT, работающий
драйвер и статус PnP OK. Подписант — Microsoft Windows Hardware Compatibility
Publisher. Test Mode выключен; VBS и изоляция памяти продолжали работать.
Настройки загрузки для этих тестов не менялись.

Получена рабочая локальная связка **одной реальной Pi5 с одной многоканальной
парой capture/render**. Опубликованный MSI/EXE 2.7.0 ACX её не включает.
Пакет производителя — demo; постоянная бесплатная производственная зависимость
пока не подтверждена. Вопросы распространения отложены.

## Два аудиотракта

| Режим | Схема | Что проверено |
|---|---|---|
| Windows-программы | Windows audio API → подписанные виртуальные устройства → микшер/служба Rey → USB | Прежняя проверка реальной Pi через USB и WASAPI; период shared-аудио 10 мс |
| ASIO/Ableton | ASIO frontend → ограниченный обмен PCM со службой через общую память → USB | [USB-ASIO](USB-ASIO.ru.md), отдельный тракт от TAG |

**Цель ниже 2 мс относится к суммарной аудиозадержке ASIO в Ableton.** Для Chrome,
Telegram и Windows shared-аудио этого требования нет. ASIO должен проходить мимо
TAG/WASAPI. Интервал USB и предыдущий цифровой RTT транспорта не измеряют
полный тракт Ableton или физическую задержку ADC/DAC.

Служба остаётся единым владельцем транспорта, чтобы Windows и ASIO могли
использовать одну Pi. USB-ASIO реализует ограниченные PCM-кольца, проверку
поколения/позиции кадров и счётчики callback/deadline. Обработка дрейфа
независимого аппаратного такта и одновременный Windows/ASIO ещё требуют проверки.

## Структура

| Файл | Назначение |
|---|---|
| `src/bridge/gateway_abi.hpp` | C API TAG 2.0, фиксированные размеры и смещения x64 |
| `src/bridge/gateway_bridge.*` | Владение SDK, формат/состояние endpoints, общие PCM-буферы и освобождение ресурсов |
| `src/bridge/driver_bridge.*` | Выбор опционального TAG или существующего ACX bridge |
| `tools/gateway/loopback_probe.cpp` | Эксклюзивный playback/capture Windows с восемью разными PCM-маркерами |
| `tools/gateway/verify_formats.py` | Изолированная проверка форматов с реальной Pi, максимум 120 секунд |

Опция сборки — `REY_ENABLE_TAG_BRIDGE=ON`; по умолчанию **OFF**. Адаптер загружает
`tagapi.dll` только из каталога EXE службы. Для зависимостей DLL используются
этот каталог и системный каталог Windows. Драйвер и SDK производителя остаются
внешними зависимостями; их бинарные файлы и цепочка подписи не изменяются.

Callback транспорта читает render-кольцо драйвера и пишет capture-кольцо напрямую.
Он задаёт аудиотакт; отдельный SDK polling-thread и дополнительная PCM-очередь
не создаются. PCM16, упакованный PCM24 и PCM32 используют свои контейнеры.
В callback нет выделения памяти. Проверяются формат, вместимость буфера и предел
кадров; переходы состояния подтверждаются, позиция устройства продвигается.
Вызовы уведомления SDK всё ещё переходят в ядро; их время входит в измеренную
обработку callback.

Используются существующие линии **TAG Speakers** и **TAG Microphone**. После
остановки службы Windows помечает endpoints как отключённые. Четыре стереопары
этот прототип не создаёт. При попытке добавить ещё одну пару render вернул `0x80070044`;
временный capture удалён. Дополнительная топология пока не подтверждена.

## Результаты

[Компактные машиночитаемые данные](evidence/rey-tag-local-20261003.json).
Во всех прогонах использовался backend Pi **digital-loopback**. ADC/DAC не
подключался и не измерялся. Вызовы службы были штатными, `digital_test=false`.

| Проверка | Измеренный результат |
|---|---|
| Нативные контракты после финальной правки кода | 24/24 |
| Принятие эксклюзивных форматов Windows | 36/36: два направления × шесть частот × три разрядности, по 8 каналов |
| Маркеры Windows → TAG → Rey → USB → Pi → обратно | 18/18 профилей; восемь правильных каналов, без неверных значений и capture discontinuities |
| Форматы | 44,1/48/88,2/96/176,4/192 кГц × PCM16/24/32; около 2 секунд проверки на профиль |
| Отдельный эксклюзивный тест 192 кГц/PCM32 | По 380 615 ненулевых кадров на канал совпали; ошибок и разрывов — ноль; эксклюзивный период Windows 3 мс |
| Непрерывность USB/службы | 300,110 с общего времени; USB-сегмент 299,823 с; 2 393 112 callback / 57 434 688 кадров |
| Счётчики этого прогона | Missing frames, layout underrun/overrun, USB errors — ноль; generation оставался 1 |
| Максимальная пауза callback/приёма | Около 1957 мкс; перцентили пауз не собирались |
| Обработка в снимке на 295-й секунде | Среднее 2,361 мкс, максимум 273,6 мкс |
| CPU службы в снимке на 295-й секунде | 12,531 CPU-секунды, 4,247% одного логического ядра |
| Одновременный shared WASAPI capture, 30,007 с | 5 748 480 кадров; один разрыв; ошибок timestamp — ноль |
| Одновременный shared WASAPI render, 30,001 с | 5 748 480 кадров; разрывов и ошибок timestamp — ноль |

Паузы уведомлений shared capture p50/p95/p99/max:
10 001,2 / 10 243,0 / 10 353,2 / 12 150,0 мкс; shared render:
10 001,2 / 10 240,7 / 10 349,5 / 12 127,6 мкс. Это интервалы уведомлений Windows,
**не ASIO-задержка и не roundtrip**. Точная причина одного разрыва capture
трассировкой не устанавливалась.

Изначальное сравнение маркеров в shared-режиме не прошло по первым двум каналам;
остальные шесть совпали. Поэтому полный 300-секундный сценарий в исходном JSON
сохраняет **false**, хотя счётчики непрерывности прошли проверку. Следующие
эксклюзивные проверки PCM совпали по всем восьми каналам в каждом профиле.
Это отделяет различие общей Windows-сессии от эксклюзивного PCM-тракта, но не
устанавливает, какое приложение, регулировка или обработка вызвали отличие.

В первой попытке матрицы тест обратился к capture endpoint во время его
переоткрытия после смены профиля (`AUDCLNT_E_DEVICE_INVALIDATED`). Для этого
условия запуска воспроизводимый тест допускает до пяти попыток. Ошибки PCM
или уже работающего потока повторными попытками не скрываются. Итоговый прогон
18 профилей использовал одну попытку на каждый профиль. Изменение формата
перезапускает USB-сессию карты; открытие/закрытие клиента внутри одного профиля
её не перезапускало.

В прогоне непрерывности SHA256 службы:
`8873305c92f0582cb0f8783cede9ebceb8076eaaba09ef9a5707362a700b85c3`.
После усиления проверок формата/ошибок матрица использовала:
`6cd319d769269cdbe05766342174da54a1b1a6f28672a92232bfe03099ec8caf`.
Это локальные тестовые binaries, а не новые release assets.

## Повторение

Установить оригинальный demo производителя его установщиком/driver manager.
Собрать Rey с `REY_ENABLE_TAG_BRIDGE=ON`, положить оригинальный x64 `tagapi.dll`
рядом с `ReyAudioService.exe`. Собрать marker probe компилятором C++17 для
Windows с библиотеками `ole32`, `uuid`, `avrt`; для MinGW нужен `-municode`.
При минимальном toolchain каталог `REY_WASAPI_HEADERS` предоставляет недостающие
WASAPI-заголовки и `mmreg.h`.

Получить ID устройств TAG через `ReyAudioProbe`, затем:

```powershell
python tools/gateway/verify_formats.py --service build/gateway/bin/ReyAudioService.exe `
  --probe build/gateway/bin/GatewayLoopbackProbe.exe --out build/gateway/proof `
  --render-id '<ID TAG render>' --capture-id '<ID TAG capture>'
```

Запускается ограниченная консольная служба с новым изолированным `.dat`
тестовым профилем. Тест не устанавливает службу, не меняет обычные настройки
карт или загрузку/защиту Windows. `.dat` — внутреннее хранилище проверки, а не
пользовательский установочный INI. Перед тестом остановить другой host/службу
Rey, поскольку TAG принадлежит одному host. Текущий локальный установщик
USB-ASIO работает отдельно от этого прототипа системных устройств.

Осталось проверить: совместную работу Windows/USB-ASIO и roundtrip/deadline в Ableton
прогонами до 300 секунд, независимый аудиотакт и ADC/DAC, сессии Chrome/Telegram,
цикл установки и дополнительную топологию endpoints. Pi4, прошивка Pi и USB
протокол в этой работе не менялись.
