# Минимальная подтверждённая задержка LAN одного Pi

**Результат: PASS 15 минут.** Поиск выполнен на одном Pi 5 через встроенные Ethernet-порты. Измеряется цифровой путь Pi → Windows service echo → Pi. ADC/DAC latency, ACX/WASAPI и реальная DAW в этот тест не входят.

Самый быстрый профиль, подтверждённый 900-секундным тестом этой серии: **block=256, guard=1024**, 8×8 каналов, 192000 Гц, PCM24, capture=32, EnergySaving=0. Искусственная нагрузка callback=50 мкс.

**Цифровой RTT p50 / p95 / p99 / max: 6.251 / 6.755 / 6.891 / 11.718 мс.** Samples=3373249; фактический PCM loop=900.004 с. Missing/late, deadline/skipped, resync, host overruns, expired output, queue/socket/control/MMCSS/IO errors и Pi loss/error counters нулевые. Приращения eth0 errors/drops нулевые.

Windows audio/RX/TX CPU: 7.212 / 3.017 / 1.929%; Pi process CPU: 7.986%. Это проценты одного логического процессора Windows или одного ядра Pi.

Callback period=1333.333 мкс; guard=5.333 мс. Полный RTT измерен отдельно; сумма этих параметров не заменяет измерение.

**Минимум относится к подтверждённым тестам этой серии.** 30-секундное окно без ошибок — только предварительный кандидат. Оно не становится подтверждением стабильности, если 15-минутный тест другого, более широкого профиля прошёл. Каждый отдельный LAN-прогон ограничен 900 секундами. Часовые тесты отсутствуют.

RTT — полный цифровой возврат через Windows echo. Односторонняя задержка здесь не измерялась; деление RTT на два не даёт проверенной capture или render latency, поскольку направления и обработка различаются.

## Как выполнен поиск

1. Зафиксированы service и Pi binary hashes, PCM24/capture32, 192 кГц, 8×8, callback50 и непрерывный PCM. Настройки Windows NIC, network priority, power plan и CPU policy Pi не менялись; CPU2/3 сохранены.
2. Block128 проверен с guard128/256/384/512/768/1024/1536 по 30 секунд. Затем block256 — с теми же guards в обратном порядке. Переход block128→256 сделан при неизменном guard1536; соседние шаги сетки меняют один параметр.
3. Рядом с лучшим коротким кандидатом проверены до двух меньших guard с шагом 64 frames, то есть 333,3 мкс при 192 кГц. Повторно уже измеренные сочетания не запускались; более мелкий шаг не исследован.
4. Из коротких окон с нулевыми error counters выбран минимальный RTT p50; при равенстве используются p99 и max. Выбранные параметры проверены 900 секунд. Стабильность требует также совпадения PID/hash Pi, нулевых eth0 errors/drops и отсутствия текущих throttle flags в снимках до/после.
5. При FAIL первого подтверждения допускается отдельный 900-секундный block256/guard1536, если его короткое окно было чистым. Между длинными окнами исходная служба восстанавливается, временный Pi peer запускается заново. Так каждый 30-минутный restoration watchdog покрывает только свой этап. Неудачный результат сохраняется; тот же профиль не перезапускается ради PASS.
6. После окончания возвращены исходные executable/command/config и eth0. Отдельный read-only postflight проверяет LAN/Wi-Fi, CPU isolation, остановку временного peer и обоих timers.

Это внешний подбор ручных настроек стенда. Автоматического изменения buffers в рабочей службе не добавлено. Windows/LAN граница 1,2 мс учитывается как ограничение задачи, указанное пользователем; её самостоятельная квалификация или повторное исследование сетевого приоритета здесь не выполнялись.

Аудиокод и оба binaries в этой серии не изменялись. Добавлены отдельный координатор поиска, общий расчёт статуса/CPU стенда и генератор отчёта из JSON. Профиль рабочего INI не переключается автоматически.

Во всех длинных окнах второй Windows owner проверяется отдельно: ожидается BUSY/exit5 при активной первой сессии. Это проверка владения, а не подтверждение PCM-стабильности.

Pi CPU рассчитан по schedstat потоков. Максимум RX gap отражает интервал наблюдения в Windows; он не устанавливает причину в NIC/IRQ/NDIS. RX gap не равен возрасту каждого packet относительно presentation deadline. Нельзя выбрать минимальный guard простым приравниванием к max RX gap: важны frame indices, фаза callback и состояние timeline; итог проверяется по missing/late и прочим counters. Повторное событие питания между снимками может не изменить уже выставленные history bits. Питание непрерывно не измерялось.

## Что означают результаты

В 900-секундном 128/448 получены late=5312, missing=5312, host_overruns=1. RX gap max=5.215 мс при guard=2,333 мс; callback max=897.6 мкс при period=666.7 мкс. Увеличение одного guard не расширяет период callback. Callback duration измеряется по wall time и может включать ожидание CPU; эти counters не устанавливают причину задержки внутри Windows.

Снижение только guard с 1536 до 1024 уменьшило измеренный RTT p50 на 2.667 мс. Оба этих профиля прошли отдельные 15-минутные окна без error counters. Сетевой расход и callback period одинаковые. Guard768/512 у block256 прошли лишь короткую предварительную проверку; их 15-минутная устойчивость не подтверждена.

## Границы результата

Подтверждение относится к этому цифровому 15-минутному окну, указанным каналам/rate/PCM и искусственному callback50. Оно не гарантирует такой же результат при другой нагрузке, driver bridge или DAW. Неподтверждённые меньшие guards могут требовать отдельных окон; глобальный математический минимум по одному поиску не установлен.
